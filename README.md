# mac-do — 自然言語でMacのGUIを操作する(完全ローカル)

「日記のフォルダを開いて」のような日本語1行の指示で、macOSアプリの中の該当するボタンや
項目を探してクリックする。判断に使うLLMはローカル(自宅LAN内のGX10で動く`chakuho`)のみ。
指示文もアプリの画面内容も外部へは一切送信しない。

```bash
mac-do "日記のフォルダを開いて"
```

## これは何をするツールか

普通、macOSの操作を自動化しようとすると「x=340, y=512をクリック」のような座標指定か、
AppleScript/Automatorでアプリごとの手順を書く必要がある。mac-doはその代わりに、
**曖昧な日本語1行→画面の中から該当する要素を選ぶ→実際にクリックする**、という
3ステップを自動でやる。「ラベルに"日記"という文字が一切無いフォルダを、"日記のフォルダ"
という指示だけで正しく選べる」のが売りで、これは決め打ちのルールではなくLLMによる
意味理解で実現している。

現状(v0.1)はクリックのみ。テキスト入力・ドラッグ・複数手順の連続実行はまだできない。

## 仕組み(3段階)

```
自然言語の指示                                                          
      │                                                                 
      ▼                                                                 
┌─────────────────┐   ┌──────────────────────┐   ┌──────────────────┐
│ ① 要素を洗い出す │──▶│ ② どれを押すか決める │──▶│ ③ 実際にクリック │
│   macOS AX API   │   │   chakuho(GX10)      │   │   CGEvent        │
│   (決定論・正確) │   │   ローカルLLM判定    │   │                  │
└─────────────────┘   └──────────────────────┘   └──────────────────┘
```

### ① 要素を洗い出す — macOS Accessibility(AX)API

対象アプリ(前面アプリ、または`--app`指定)のプロセスに対し、macOSの標準機能である
Accessibility APIで画面上のボタン・テキストフィールド・メニュー項目などを全部
列挙する。この時点で各要素の**正確な座標**(クリックすべきx, y)が決定論的に取れる
——ここにLLMは一切介在しない。座標を間違えることは原理上ない。

Electron製アプリ(Obsidian等)はデフォルトでAX木を公開しないため、
`AXManualAccessibility`属性を明示的にONにしてから読む。

### ② どれを押すか決める — chakuho(GX10のローカルLLM判定サービス)

洗い出した要素一覧(役割・ラベル)と、ユーザーの指示文を、自宅LAN内のGX10(専用の
GPUマシン)で常駐しているLLM判定サービス`chakuho`に送る。chakuhoは文章を生成する
代わりに、**候補それぞれについて「これが正解である確率」を1回の推論で返す**
(詳しくは後述)。これによって「日記のフォルダ」→ラベルに"日記"の文字が無い
`03_Diary`というフォルダ、のような曖昧な意味マッチングができる。

chakuhoは3つを判定する:
- **target**: どの要素を操作すべきか(確率つきで1つ選ぶ。「該当なし」も選択肢の1つとして
  明示的に用意してあり、コインフリップ的な確信度の低さと「本当に無い」は区別される)
- **risk**: その操作がどれくらい危険か(安全 / 要注意 / 破壊的)
- (**done**: 目標がもう達成済みかどうかも判定できる設計だが、mac-doは単発クリックのみで
  複数手順のループを持たないため現状は未使用)

### ③ 実際にクリックする — CGEvent

②で選ばれた要素の①で取得済みの座標へ、macOSの`CGEvent`でマウスクリックイベントを
直接送る。これもLLMを介さない決定論的な操作。

## なぜ座標までLLMに読ませないのか

画面のスクリーンショットを画像としてLLM(VLM)に渡し「どこをクリックすべきか座標を
答えさせる」方式(ピクセル接地)も検討したが、実験でy座標の正方形規約のズレや
密なリストでの1行ズレなどの誤差が頻発し、採用しなかった(検証の経緯は開発ログ参照)。
**座標のような「間違えると即事故る決定論的な値」はAPIから正確に取り、LLMには
「意味的にどれが正しいか」という曖昧さの処理だけを任せる**、という役割分担が
mac-doの核。

## 安全装置(3段構え)

誤クリックはファイルの削除やアカウントの喪失につながりうるため、複数の独立した
チェックを重ねている。上から順に強い順:

1. **DANGEROUS正規表現(常に最優先・authoritative)**: 選ばれた要素のラベルに
   「削除」「Delete」「ゴミ箱」「Trash」等の語が含まれていたら、他の判定に関係なく
   `--force`なしでは絶対に押さない
2. **chakuhoのrisk判定(追加の網)**: 正規表現に引っかからなくても、chakuhoが
   「安全」以外(要注意・破壊的)と判定した場合、または判定自体の確信度が低い場合は
   `--force`を要求する。この判定は「選ばれた要素単体」だけでなく候補全体の文脈を見て
   いるため、やや保守的(≒空振りが増える方向)に倒れる作りになっている
3. **確信度(coverage)チェック**: chakuhoの選択結果の確信度が低い場合は「判定不能」
   として、押さずに終了する

さらに、**判定サービス(chakuho)自体が落ちている時に誤動作しない**設計にしてある:
既定では「chakuhoに繋がらない→判定不能として何もしない」で止まる。ローカルの
Ollamaへこっそり切り替えて動き続ける、という挙動はしない(黙って代替経路に
切り替わると「気づいた時にはずっと別のモデルで動いていた」という事故につながる
ため、意図的に「気づける形で止まる」を既定にしてある)。`--fallback-ollama`を
明示指定した時だけ、警告ログを出しながら旧経路(ローカルOllama)へ切り替える。

## 使い方

```bash
mac-do "日記のフォルダを開いて"            # 前面アプリに実行
mac-do --app Obsidian "設定を開いて"       # アプリ指定
mac-do --dry-run "..."                     # 選択のみ表示(クリックしない)
mac-do --list --app Obsidian               # AX要素一覧を出すだけ
mac-do --force "..."                       # 破壊的ラベル安全装置の解除
mac-do --fallback-ollama "..."             # chakuho不通時にOllamaへ降格を許可(既定は禁止)
```

ランチャー: `~/bin/mac-do`(このrepoの`.venv`を叩くだけ)

## セットアップに必要なもの

- **Accessibility権限**: 画面の要素を読むにもクリックするにもmacOSのAccessibility
  権限が要る。「システム設定 > プライバシーとセキュリティ > アクセシビリティ」から手動で
  許可する(コマンドラインからは付与できない)。付与先はmac-doを起動したターミナル
  アプリ(macOSの「責任プロセス」)またはpython本体。付与済みかは次のコマンドで確認できる:
  `.venv/bin/python -c "import ApplicationServices as A; print(A.AXIsProcessTrusted())"`
  (`False`なら未付与。未付与だと`--list`が要素0件・exit 0で無言終了する。2026-09-19に
  この症状を観測し、後に同じ環境で`True`になって取得できるようになった。付与先が
  ターミナルアプリとpython本体のどちらだったかは未特定)
- **chakuhoの接続先**: 環境変数`CHAKUHO_URL`で判定サービスのURL
  (`http://<GX10のアドレス>:9750/v1/systemone`の形)を指定する。未設定の場合は
  `http://localhost:9750/v1/systemone`を見に行く。自宅の環境では、この変数を
  ランチャー(`~/bin/mac-do`、リポジトリ外)で設定している。接続先に届かない、または
  chakuhoが落ちている場合は「判定不能」で終了する(上記の安全装置を参照)
- **(任意)ローカルOllama**: `--fallback-ollama`を使う場合のみ必要

## 制約・既知の問題

- クリックのみ(v0.1)。テキスト入力・ドラッグ・複数手順の連続実行は未実装
- AXが薄いアプリ(ラベル無しcanvas描画など)は対象外。ブラウザ内WebページはChrome用の
  別ツールの領分
- Electronアプリは`AXManualAccessibility`を明示的にONにしないとAX要素が空で返る
- chakuhoの`done`(目標達成済み判定)は用意されているが、複数手順ループを実装するまで
  未使用

## ベンチマーク(2026-09-19、GX10実測。vLLMに他リクエストが同居した状態での計測)

出典: gx10-claude(GX10側セッション)による実測。計測スクリプト(`agree_eval.py` /
`lat_bench.py`等)はGX10側で管理している。数値は本番環境の混雑状況に依存するため目安として扱う。

### chakuhoのレイテンシ(候補要素数別)

| 要素数 | target単問 p50/p95 | target+risk+done 3問 p50/p95 | 入力トークン |
|---|---|---|---|
| 8   | 0.61s / 0.62s | 0.69s / 0.69s | 356 / 556 |
| 32  | 0.88s / 0.88s | 1.01s / 1.01s | 1,138 / 1,338 |
| 100 | 3.18s / 3.18s | 3.27s / 3.28s(内部2段トーナメント) | 5,212 / 5,412 |
| 233 | 6.35s / 6.36s | 5.26s / 5.26s(内部2段トーナメント) | 10,258 / 10,458 |

32要素までは1秒未満。100要素を超えると内部トーナメント(52件ずつのチャンクに分割し
並列判定→決勝)が発動し数秒規模になる。参考値として、LAN越しの3要素同時判定は522ms、
別ベンチ(jev-mario、9択・入力1,100トークン)はp50 0.855s。

### 「小型モデルへ差し替えられるか」の検証結果(重要)

mac-do/chakuhoの判断をより軽量なモデルに置き換えられないか検証した結果、
**汎用の小型instructモデルをゼロショットでそのまま使うのは不十分**という結果が出た。

測定方法: 判定ログ+合成GUIケース12件(カレンダー画面28要素+`__none__`、教師は本番
chakuhoの27B NVFP4)。比較対象の小型モデルはollamaネイティブAPI経由でchakuhoと
同一プロンプト・同一集約ロジックを使用。対照としてollamaのqwen3.8:27b(本番と同一
モデルだが別backend/量子化)も流し、backend差によるノイズ床を測った。

> [!note]
> 初回報告時のmario列は母数49件だったが、負荷計測用の合成要素とjev-mario(下記参照)が
> 詰まって同じ状態を繰り返し送っていた重複を含んでいたと後日判明した(2026-09-19、
> gx10-claude訂正)。重複除去後の実際の母数は23件で、以下の表の数値は**訂正前**のもの。
> 比率の傾向(4B/8B低・27B高)自体は重複除去後も変わらないとの報告だが、正確な値は
> Jev本家との基準線比較が終わり次第差し替える。**GUI 28択の列(母数12件)は重複の影響を
> 受けておらず、そのまま有効。**

| モデル | choice一致(mario 9択、母数49→実際は23) | choice一致(GUI 28択) | noul平均差 | score平均差 | coverage中央値 | 1リクエスト |
|---|---|---|---|---|---|---|
| `qwen3:4b-instruct-2507`(Q4) | 10/49 (20%)、訂正前 | 6/12 (50%) | 0.29 | 0.09 | 1.00 | 0.14s |
| `qwen3:8b`(think off、Q4) | 5/49 (10%)、訂正前 | 8/12 (67%) | 0.04 | 0.06 | 1.00 | 0.21s |
| `qwen3.8:27b`(ollama Q4、対照) | 44/49 (90%)、訂正前 | 11/12 (92%) | 0.03 | 0.05 | 1.00 | 1.85s |

読み: 同じ27Bでもbackend(ollama Q4 vs 本番のvLLM NVFP4)が違うだけで1割ずれる
(ノイズ床≈90%)。4B/8Bのゼロショットはこのノイズ床から遠く、GUI 28択でも50〜67%止まり
——**「小型の汎用モデルをそのまま使う」では足りない**。8Bはnoul/score(達成判定・危険度)は
27Bに近い値を出せているので、弱いのはchoice(候補の意味照合)側。しかもcoverageはどのモデル
でも中央値1.00で、「答えの形式(確信度が高いという体裁)は守るが中身が違う」型のため、
coverageの閾値チェックでは誤りを検出できない。
→ 行き先の選択肢: (a) GX10の判定ログを教師データに専用モデルを蒸留する、(b) 27Bのまま
GX10へ依存し続ける。基準線としてJev本家(Vercel AI Gatewayで無料枠提供中、2026-09-19時点
レート制限待ち)にも同じデータを流して比較する案が進行中。「27B chakuhoがJev本家とどれだけ
一致するか」は蒸留の教師として27Bを使ってよいかの根拠になるため、結果待ち。

### Jev本家との基準線比較(2026-09-19 21:20、Vercel AI Gateway経由・GX10から実行)

上記の重複を除去した実データ(35件: GUI 12 / マリオ23)を、判断モデルの本家である
Jev自身にも流し、chakuhoやollama小型モデルがJevとどれだけ一致するかを比較した
(基準=Jevのchoice)。

| モデル | GUI 12件との一致 | マリオ23件との一致 | noul平均差 | score平均差 |
|---|---|---|---|---|
| chakuho 27B(vLLM本番) | 10/12 (83%) | 9/23 (39%) | 0.09 | 0.05 |
| `qwen3.8:27b`(ollama Q4) | 11/12 (92%) | 7/23 (30%) | 0.10 | 0.09 |
| `qwen3:8b` | 10/12 (83%) | 15/23 (65%) | 0.15 | 0.02 |
| `qwen3:4b-instruct-2507` | 7/12 (58%) | 11/23 (48%) | 0.21 | 0.05 |

Jev自身の最尤確率は中央値0.76で、35件中14件は0.5未満(マリオの一部はJev自身も
迷っている)。Jevのレイテンシ中央値は578ms(Gateway経由・GX10→米国のネットワーク
遅延込み。README内の他のJev参考値[0.24s台]は米国内計測のため単純比較不可)。

読み: **GUIの要素選択では27Bも8Bも約8割強でJevと一致し、この差は27B同士の
backend差(8〜10%)と同程度**——この範囲ではchakuhoはJevと同等とみなせる。ただし
n=12と少なく、8Bと27Bどちらが優れるか(=蒸留や小型化の要否)はまだ判別できない。
マリオ側は全モデルの一致率がバラバラ(30〜65%)で、これはモデル差というより
問題自体の難しさ(Jev自身も自信が低い)を反映しており、モデル比較の材料にはならない。

**jev-mario再現(本物のJev、GX10からGateway経由)**: 直接操作686 / 476 / 607
(ステージ1-1/2-1/3-1)、liveモード1-1は312。上記「設計時の参考値」に記載した
Jevの数値(686 / 473 / 607〜841、315)と一致し、chakuho(qwen3.8-27b、401 / 308 / 445)
との差は実測で確定した。

**蒸留判断への含意**:
- 27Bを教師にする案: GUIでJevと83〜92%一致するため教師として使える水準。ただし
  JevもchakuhoもGUI以外(マリオ)では自信の低いケースがあるため、教師データにする際は
  「Jevと27B両方が同じ答えを出したケースだけ採用する」合意フィルタを掛けるのが安全
- 8Bで足りるか: n=12では27Bと同等に見えたが判別に足りなかったため、実画面336ケースで
  再検証した(次節)。**結論は「8B/4Bは不十分」**

### 実画面336ケースのベンチマーク(2026-09-19、GX10実測)

macOSの実アプリ11画面(通常ウィンドウ8+シート/ダイアログ3。アクセシビリティ木を取得し
個人情報をマスク済み)から112タスクを作り、各タスクを3変種(そのまま / 要素順シャッフル /
別アプリの要素15個を混入)で流した。候補は1画面26〜233要素+`__none__`。期待答えは作題者が
決め、`__none__`が正解のタスクを39件含む。Jevは Vercel AI Gateway 経由、chakuhoは27B
NVFP4(vLLM)、小型モデルはOllamaで同一プロンプト・同一集約。

| モデル | 通常画面 258件 | シート 78件 | 通常: `__none__`正解 30件 | 順序シャッフル/混入で落ちるか |
|---|---|---|---|---|
| chakuho: Qwen3.8-27B NVFP4 | **245 (95%)** | **72 (92%)** | 29 (97%) | 落ちない(93→97→95%) |
| Jev(`typesafe-ai/jev`) | 230 (89%) | 64 (82%) | 27 (90%) | 落ちない(85→91→92%) |
| Qwen3-8B(thinking off) | 162 (63%) | 34 (44%) | 3 (10%) | 落ちる(67→60→60%) |
| Qwen3-4B-Instruct-2507 Q4 | 157 (61%) | 33 (42%) | 3 (10%) | 落ちる(66→58→58%) |

同じ要素を選んだ割合は、Jev×chakuho 86%(通常)/90%(シート)、Jev×8B 58%、8B×4B 93%。

- **27Bのchakuhoは、Jevと同等以上。** 差の大半はシステム設定(Jev 78% / chakuho 88%)と
  Docker Desktop(87% / 98%)で、要素名が抽象的な画面でJevが迷う
- **8B/4Bは足りない。** 「該当なし」を30件中3件しか選べず、候補の順序や他アプリの要素の
  混入で崩れる。8Bと4Bの答えは93%同じで、間違え方も同じ。前節の「8Bも8割」はn=12の
  小ささによるもの。小型モデルを使うなら、chakuhoの判定ログからの蒸留が要る
- **破棄確認シート(削除/キャンセル/保存)の危険な取り違えは、Jev・chakuhoともゼロ。**
  両者が落とした残りは、作題者の期待(`__none__`)が厳しすぎるもの(「書類を印刷する→
  ファイルメニュー」)と、解釈が割れるもの(「削除せず何もしない→`__none__`」)

### 設計時の参考値(chakuho開発時のベンチマーク)

- vLLM `qwen3.8-27b` NVFP4(`:8006`、max-num-seqs 112): 1判定0.6秒、6問並列1.13秒、
  24問並列4.0秒(≒毎秒6判定)。prefix cacheはQwen3.5系ハイブリッドアーキテクチャの
  ブロック単位が1,600トークンのため短文では効かない(hit率0%)
- Ollama `qwen3.8:27b` Q4_K_M: prefill約520 tok/s、decode 16 tok/s(GB10の帯域上限)。
  logprobsは先頭1トークンのみ返る(MTP投機デコードの副作用と推定)
- 旧方式(thinkingモデルにJSON生成させidを抽出)との比較(同条件6問): thinking OFF
  2.3〜3.5秒、thinking ON 80秒、chakuho型(logprob判定・6問並列) 1.13秒
- **jev-mario再現ベンチ(直接操作、ゴールまでの到達距離x、値が大きいほど良い)**:
  `qwen3.8-27b` 401 / 308 / 445(ステージ1-1 / 2-1 / 3-1) vs Jev本家 686 / 473 /
  607〜841 vs ルールベース 1129 / 741 / 608。branchモード(1-1): qwen 2370、Jevは
  旗(ゴール)到達、ルールベースも2370。liveモード(1-1)は3者とも315で並ぶ
- 判断の既知の弱点: 数値条件つきルール(「届かないかつ6タイル未満なら後退」等)の誤適用が
  多い。意味照合は得意、算術判断は不得意(このためmac-doでは危険操作の判定を正規表現+
  risk判定の二重化にしている。数値条件をLLMに委ねていない)
